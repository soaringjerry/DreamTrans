# 注册赠送风控

后台 `/pro/admin` →「注册风控」。保护的是自助注册的试用余额、活动余额和赠送套餐，
不是按 IP 封禁账号。触发规则后仍可创建账号、验证邮箱、登录和正常付费使用；
自动赠送暂缓，管理员核实后填写备注放行或拒绝赠送。

## 默认规则

- 同一个浏览器标识：30 天内第 2 个账号开始复核。
- 同一个网络：滚动 24 小时内第 6 个账号开始复核。IPv4 按地址，IPv6 按 /64 网络。
- 全站：滚动 24 小时自动放行 100 个新注册后暂缓后续自动赠送资格。
- 缺少有效的服务端签名浏览器 Cookie、无法确认来源网络，或命中历史邮箱摘要：复核。
- 现有邮箱格式、一次性邮箱域名、规范化邮箱唯一性、邮件验证和 API 限流继续生效。

后台可调整前三项阈值或关闭自动暂缓（仅观察新注册的信号）。关闭不会释放已有待审账号。
计数包含尚未验证和已删除账号；全站上限针对新注册的自动放行数，不是实际到账金额或
信用额度。多人共用电脑、校园/公司网络都可能触发复核，不能仅凭信号判定欺诈。

## 管理员与用户流程

注册时在同一个 PostgreSQL 事务内评估并保存来源、风险和账号。短事务通过数据库锁
跨进程串行评估，避免并发绕过阈值。规则快照、各信号计数和原因随账号保留。

用户在注册后的邮件验证页与账户余额页可看到「赠送权益审核中」或未通过提示，以及
联系 support@coyume.com 请求复核的方式。前端不能提交评分或决定放行结果。

管理员可以按状态、邮箱、昵称、渠道筛选；复核必须填写备注。通过后，已验证且启用
的账号立即尝试领取试用和活动权益，未验证账号在邮件验证后领取。账本事务检查风险
状态，反复审核、验证或登录不会重复发放。发放失败可重试批准或由用户重新登录重试。
已放行的权益不能通过审核操作追溯撤销；账户封禁与人工余额调整继续走原有后台流程。
所有规则修改和审核操作存入 `signup_risk_audit`。

管理员主动创建的账号、既有账号不自动进入新的风控队列；管理员主动手工赠送属于
独立的受权管理操作。上线前已删除的账号没有可回溯的浏览器/IP 风险记录。

## 浏览器标识与隐私

注册提交前访问 `/api/auth/signup-context` 获取 `dt_signup_device`：服务端签名的随机值，
30 天有效，HttpOnly、SameSite=Lax；HTTPS 配置下使用 Secure。它不是登录凭证，
不采集硬件指纹，不跨站追踪。清除 Cookie、使用另一浏览器或分布式代理仍可能绕过
部分规则，所以系统降低批量领取风险，不能证明真实身份或保证一人一号。

数据库只记录带服务端密钥的 HMAC，不在风险接口暴露明文 IP、Cookie 或其摘要。
浏览器/网络关联摘要在 30 天后由每日清理任务清除（通常不超过 31 天）；审核证据和
邮箱 HMAC 保留以识别删除重建账号。这些仍是受保护的数据，按部署方保留策略管理。

## 配置与部署

- 新迁移：`037_signup_risk.sql`，迁移后再运行新后端。
- `SIGNUP_RISK_SECRET`：可选、至少 32 字节的独立稳定密钥；未设置时使用 `JWT_SECRET`。
  建议上线前配置独立密钥并备份。更换密钥会使旧 Cookie 失效、旧邮箱摘要无法关联，
  所以轮换 JWT 时应保留独立风控密钥。
- `APP_BASE_URL`：设置为真实 HTTPS 站点地址，保证 TLS 终止代理后仍发 Secure Cookie。
- `TRUSTED_PROXY_CIDRS`：仅填写实际反向代理的地址网段。系统与现有限流使用同一套
  客户端 IP 解析：未受信代理的 X-Forwarded-For 不被采信。未配置时按直连对端统计；
  如果所有访问经过代理，会把它们看作同一网络。不要为方便设置成信任整个互联网。
- 所有用户使用同一站点的前后端即可发送 Cookie；跨站前后端若浏览器阻止 Cookie，
  会进入人工复核。普通 API 注册客户端同样需要保留该 Cookie。

后续如遇分布式批量滥用，可在这套复核入口上接入验证码、手机号或支付平台的验证
结果；本版没有强制用户绑卡，也不接收卡号或证件。
